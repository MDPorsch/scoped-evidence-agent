## WHAT TESTING FOUND IN MY OWN WORK

* **20 survivors in the first mutation run, all in my tests, none in the code under them.** The verdict-word test iterated the very set it was
  checking, so removing a word removed its test. Several reply-shape tests used truncated JSON that is rejected anyway, so the check that
  catches a *perfect-looking* reply was never exercised (the token cap, a key echoed inside valid JSON, an oversize reply, a repeated id).
  The CLI paths for host masking, passing the key to the checks, the hint after `run`, and refusing to replace a broken configuration
  had no test that failed without them. A refusal counted as a call, a negative token count and the audit decision of a failed call were never
  asserted. One of the survivors was hiding two layers that guard the same property; its mutant now removes both.
* **A real bug, found by a unit test:** the protected-token pattern for a path swallowed the sentence's final full stop, so a wording that
  kept the path but moved the stop was wrongly refused.
* **Coverage fell to 99.7% at the gate** (the operating-system failure paths of the configuration file, the Claude branch of the factory, the
  length check after hosts are put back, a draft made before there were details). Each now has a test; the gate is 100% again.
* **The SDK reads credentials from the environment.** `ANTHROPIC_AUTH_TOKEN` would have been sent as a bearer header to the fixed endpoint
  whatever the configuration said. Passing the key explicitly turns that off (the SDK treats an explicit argument as total); a test pins it
  and checks that `ANTHROPIC_BASE_URL` cannot redirect the client either.
* **Lint caught a procedure that had grown too long** (`reword_run`: 59 statements); it is now small helpers around a result record.

## WHAT THIS DOES NOT SHOW

* **That a wording is good.** The checks keep every number, date, version, header, path and host and refuse verdict words and markup, but
  they cannot tell that a sentence still *means* the same (SE-32). The rule's text is always shown first and the wording is labelled.
* **That it is cheap or fast.** No real call was made, so no cost or latency was measured. The default model is `claude-opus-5-5`; a smaller
  one such as `claude-haiku-5-5` is enough for rewording and costs less (`ai enable --model`).
* **That nothing leaves except what is documented, on a machine that is not mine.** The tests pin what is sent and that `run` never builds an
  adapter; they cannot see the network, only the code. `docs/ai-adapter.md` lists exactly what is sent so you can read it before typing `enable`.
* **Mutation testing shows the tests notice these bugs, not that no other bug exists.**
