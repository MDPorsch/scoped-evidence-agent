## WHAT TESTING FOUND IN MY OWN WORK

* **A real defect, found by running the first fixture:** the finding schema only allowed rule ids of up to five letters, so `R-COOKIE-01`
  made the whole run fail with `ValidationError while correlating`. The pattern now allows eight letters (boundary tested both ways).
* **One mutant survived:** the "a change of state is not drift" test used `DELETE` and `POST` on paths the scope already lists, so it could not
  tell a rule that flagged them from one that did not. It now uses paths the scope does not list, with a control.
* **Two small deviations from the approved design**, both on the safe side: (1) cookie flags are recorded for *every* HTTP response, not only when
  the check is on, because the adapters do not see the scope. They only add facts: no request and no draft changes unless the check is on.
  (2) A **missing** `Referrer-Policy` is not flagged (the design listed it): current browsers default to a protective policy, so flagging
  absence would be noise; only `unsafe-url` is. `R-HDR-01` still reports a missing HSTS, CSP or X-Content-Type-Options.

## WHAT THIS DOES NOT SHOW

* That a flagged cookie is sensitive: the tool never sees a value, so every draft asks the owner (`LIMITATIONS.md` SE-48).
* That a policy that passes is good: the CSP reading is a judgment (a nonce, hash or `'strict-dynamic'` neutralises `'unsafe-inline'`), and it
  judges the responses collected, not every page.
* `spec_drift` compares paths only, GET and HEAD only, and says nothing when the description's list was cut short.
* Nothing was run against a real host in this stage: none of it needs to be.
